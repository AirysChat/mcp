## 3. Quirks & non-obvious behaviour

1. **Live Operations Gate (`403 { error: "meta_business_agent_live_operations_disabled", safety: ... }`)**:
   - In `Saas::Api::V1::AiManager::MetaBusinessAgentWorkspacesController`, every action except `show`, `bootstrap`, and `confirm_terms` runs `require_live_operations!` (`AiManager::MetaBusinessAgent::LiveOperationsGate.live_enabled?`). When live Meta operations are disabled for the account/phone (e.g., on staging demo inboxes without a live Meta WABA token), the controller returns `403` with `error: "meta_business_agent_live_operations_disabled"` and a `safety` object. Curated tools surface this structured safety payload cleanly so operators can see why live Meta calls are gated.
2. **Idempotency key & optimistic concurrency (`observed_hash`)**:
   - `AiManager::MetaBusinessAgent::Command#call` requires `idempotency_key` (a non-empty string identifier without spaces or commas, max 255 bytes) on every non-read workspace command. Curated write tools generate a deterministic or UUID `idempotency_key` automatically when the caller omits it.
   - `update_settings`, `update_business_info`, and `reset_business_info` require `observed_hash` matching the current `GET` snapshot (`409 { error: "observed_snapshot_conflict" }` on mismatch) and perform readback verification (`502 { error: "meta_readback_mismatch" }` if Meta's readback differs). Curated write tools fetch the current snapshot (`observed` + `observed_hash`) before confirmation and pass `observed_hash` automatically when confirmed.
3. **Thread control takeover vs. release**:
   - Takeover has **no API endpoint**: sending the first human agent reply in AirysChat automatically takes thread control from Meta Business Agent.
   - Releasing thread control back to Meta (`POST /conversations/:conversation_id/meta_business_agent_control`) only accepts `thread_control_action: "release"`, requires the conversation to be in handoff state (`status == "handoff"`) with confirmed app ownership that has settled past `TAKEOVER_SETTLE_DELAY`, and requires an active `canary` or `public` Meta deployment.
4. **Handoff rotation vs. Meta handoff message**:
   - Meta decides *when* to hand off and sends `settings.handoff.message` (`mba_settings_get` / `mba_settings_update`).
   - AirysChat decides *which human agent* receives the handed-off conversation via `GET/PUT /api/v1/accounts/:account_id/meta_agent/inboxes/:inbox_id/handoff_assignment` (`mba_handoff_get` / `mba_handoff_update`), where every `user_id` must belong to `inbox.members` and `weight` must be `1..10`.
